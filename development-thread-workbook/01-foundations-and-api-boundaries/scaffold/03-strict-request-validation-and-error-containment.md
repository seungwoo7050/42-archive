# Strict request validation과 내부 오류 격리

- 카테고리: `01-foundations-and-api-boundaries` — 애플리케이션 기반과 API 경계
- Repository: `https://github.com/seungwoo7050/42-archive`
- Branch: `web/ft_transcendence`

## 1. Thread 목표

부분적으로 적용되던 route validation을 모든 JSON route의 strict params/query/body 경계로 통합하고 client error와 internal processing error의 노출 범위를 분리하는 과정을 복원합니다.

이 문서는 완성된 해설이 아니라 exact SHA를 순서대로 확인해 구현 발전을 복원하기 위한 scaffold입니다.

### 직접 연결되는 불변식

- untrusted HTTP 입력은 business logic 전에 strict schema를 통과해야 합니다.
- 내부 SQL, host, stack, raw exception message는 HTTP/WebSocket client response에 포함되지 않습니다.
- 잘못된 proxy header는 명시적으로 trust한 환경이 아니면 identity/rate-limit key를 바꾸지 못합니다.

## 2. 핵심 질문

- strict object가 unknown query/body field를 어떤 schema branch에서 거부합니까?
- body가 없는 route와 empty object를 요구하는 route를 어떻게 구분합니까?
- validation error의 field path와 internal error의 public message는 어떤 경계에서 만들어집니까?
- WebSocket parser error와 command 처리 중 repository error가 같은 close/message 경로를 사용하지 않는 이유는 무엇입니까?

## 3. 완료 기준

- Commit map의 모든 SHA를 지정 브랜치 ancestry에서 확인합니다.
- 각 SHA의 parent 또는 직전 관련 SHA와 비교해 변경 전후 상태를 구분합니다.
- 파일, symbol, caller/callee, 상태 mutation, failure branch, cleanup을 실제 코드로 기록합니다.
- Fix는 이전 가정과 root cause를, test는 production path와 증명/비증명 범위를 연결합니다.
- 마지막 SHA까지만 사용해 Thread 최종 owner, invariant, execution flow를 작성합니다.
