# 정렬 전략과 연산 비용

## rank가 값의 순서를 보존한다

실제 값의 크기는 정렬 전략에 필요하지 않고 상대 순서만 필요하다. 예를 들어
`[-20, 500, 7]`의 rank는 `[0, 2, 1]`이다. 입력이 중복 없이 `n`개라면 다음
불변식이 성립한다.

```text
0 <= ranks[i] < n
values[i] < values[j]  <=>  ranks[i] < ranks[j]
각 rank 0..n-1은 A와 B 전체에 정확히 한 번 존재한다.
```

파서는 값 `n`개를 복사해 `qsort`하고, 인접 중복을 확인한 뒤 각 값을 lower
bound 이진 검색한다. 통상적인 `qsort`의 비교 비용을 O(n log n)으로 모델링하면
전처리도 O(n log n), 정렬 복사본은 O(n) 추가 공간이다. C 표준 API인 `qsort`
자체의 구체적인 알고리즘과 내부 자원은 이 저장소가 통제하거나 계측하지 않는다.

모든 스택 연산이 value와 rank를 한 쌍으로 옮기므로 알고리즘이 rank만 비교해도
최종 value 순서가 보존된다.

## 0~5개를 직접 닫는다

`sort_stack`은 size < 2 또는 이미 정렬된 A를 명령 없이 성공시킨다.

| 크기 | 전략 |
| --- | --- |
| 2 | 역순일 때만 `sa` |
| 3 | top 세 rank의 여섯 상대 순서를 `sa`, `ra`, `rra` 조합으로 구분 |
| 4~5 | 현재 최솟값을 더 가까운 회전 방향으로 top에 놓고 `pb`; A가 3개면 전용 정렬; `pa`로 복귀 |

4~5개에서 작은 rank부터 B로 보내면 뒤에 뽑은 더 큰 최솟값이 B top에 놓인다.
따라서 마지막 `pa` 반복은 더 큰 값부터 A top에 붙이고, 최종적으로 작은 값이
맨 앞에 오게 한다.

작은 입력 전용 분기는 일반 radix보다 명령을 줄이기 위한 선택이지 모든 입력의
최단 명령열 증명은 아니다. 크기 2~5의 152개 전체 순열 검사는 현재 분기의
정확성을 강하게 뒷받침하지만 각 결과가 최소 명령 수라는 것을 검사하지 않는다.

## 6개 이상은 stable LSD radix다

필요한 bit 수는 최대 rank `n - 1`의 최고 set bit까지다. 각 bit 라운드 시작에
A의 크기 `n`을 `round_size`로 고정하고 정확히 그 수만큼 원소를 본다.

1. 현재 top의 bit가 1이면 `ra`로 A bottom에 보낸다.
2. bit가 0이면 `pb`로 B top에 보낸다.
3. `round_size`개를 모두 본 뒤 B가 빌 때까지 `pa`한다.

1인 원소는 A에서 rotate되는 순서가 유지된다. 0인 원소는 B에 역순으로 쌓이지만
전부 `pa`할 때 한 번 더 뒤집혀 원래 상대 순서로 돌아온다. 그러므로 현재 bit를
기준으로 안정적으로 분할하면서 이전 라운드가 정한 낮은 bit 순서를 보존한다.
마지막 라운드 뒤에는 rank 전체가 오름차순이고 B는 비어 있다.

rank 집합이 항상 `0..n-1`이므로 같은 `n`의 radix 경로는 입력 순서와 무관하게
같은 bit 수와 bit별 0 개수를 갖는다. 명령의 종류 순서는 입력에 따라 달라도
총 명령 수는 크기로 정해진다. 이 결정성은 최적성이나 모든 환경에서의 같은
벽시계 시간을 뜻하지 않는다.

## 논리 명령과 배열 이동은 다른 비용이다

| 단계 | 논리 비용 | 추가 공간 | 현재 배열 표현의 물리 비용 |
| --- | --- | --- | --- |
| token parse·rank | 통상 O(n log n) 비교 | rank 정렬 복사본 O(n) | 값 복사와 이진 검색 포함 |
| tiny sort | n <= 5라 상수 범위 | B 배열 외 추가 알고리즘 공간 O(1) | 각 rotate/push가 배열 앞부분을 이동 |
| radix | bit 수 O(log n), 명령 Θ(n log n) | 추가 알고리즘 공간 O(1) | 명령당 최대 O(n) 쌍 이동, 최악 O(n² log n) |
| checker 재생 | 명령 수에 비례 | 명령 buffer O(1) | 같은 배열 연산 비용을 다시 부담 |

`stack_push`는 목적지 앞을 열고 원본 앞을 당기며, rotate와 reverse rotate도
`memmove`로 연속 구간을 옮긴다. 따라서 push/rotate 명령 하나를 “스택 연산
1회”로 세는 논리 비용과 실제 `(value, rank)` 쌍 이동량은 같지 않다.

두 제품은 A와 B 각각에 value/rank 배열을 최초 입력 capacity만큼 할당하므로
주요 상주 저장 공간은 O(n)이다. rank 계산 중 정렬 복사본도 O(n)이지만 B는
그 복사본을 해제한 뒤 만든다. checker는 명령 하나당 4바이트 buffer만
유지하고 전체 스트림을 저장하지 않는다. 반면 stdout pipe/file과 Python
interpreter, libc 내부 자원은 제품의 프로젝트 allocator 수치에 포함되지 않는다.

## 검사가 증명하는 범위

`tests/resource_tests.py`는 고정된 크기 10, 100, 500과 세 seed에서 다음을
baseline과 비교한다.

- stdout 명령 수와 내부 `PS_OPERATIONS`
- 연산 함수가 기록한 논리적 `(value, rank)` 이동 수
- `ps_malloc`을 거친 동시에 살아 있는 프로젝트 할당 byte
- 종료 시 프로젝트 할당이 모두 해제됐는지

기능 검사는 크기 2~5의 모든 순열, 정해진 seed/크기, 크기 100과 500의 명령
상한을 다룬다. 이 증거는 작은 상태 공간과 선택한 큰 사례의 회귀를 찾지만
다음을 증명하지 않는다.

- 6개 이상 모든 순열의 정당성이나 명령 최소성
- C `qsort`, `memmove`, stdio 밖 kernel buffer의 내부 자원
- Python interpreter 비용을 포함한 제품 메모리 상한
- timeout 이내 통과를 넘어선 벽시계 성능 목표
- 실제 CPU cache traffic과 byte 단위 이동량

벽시계 시간은 resource script가 출력하는 참고값이며 baseline 합격 기준이
아니다. 명령 전략이나 저장 표현을 바꿀 때에는 명령 수, 배열 이동, 할당량 중
무엇을 줄이고 무엇을 늘렸는지 따로 비교해야 한다.
