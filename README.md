# 42 Archive

42 프로젝트와 이를 확장·재구성한 프로젝트의 **최종 구현 및 개발 이력을 보관하는 아카이브 저장소**입니다.

각 프로젝트는 독립된 **orphan branch**로 관리합니다. 브랜치 사이에 Git history의 부모·자식 관계는 없으며 `main`은 프로젝트 코드를 포함하지 않고 저장소의 공통 개발 원칙과 관리 방법만 설명합니다.

## 개발 원칙

### 1. 요구사항과 정확성을 우선한다

다음 순서로 판단합니다.

1. 안전·보안·법적 요구사항
2. 명시적인 프로젝트 요구사항과 공개 계약
3. 기능 정확성, 데이터 무결성, 호환성
4. 변경 책임의 분리와 검증 가능성
5. 빌드·테스트·릴리스 품질
6. 커밋 크기·형식 등 히스토리 규칙

커밋 형식이나 변경량 기준을 맞추기 위해 정확성이나 원자성을 희생하지 않습니다.

### 2. 하나의 커밋에는 하나의 변경 목적을 둔다

각 커밋은 하나의 주된 책임과 하나의 리뷰 질문으로 설명할 수 있어야 합니다.

같은 커밋에 포함할지는 다음 세 가지를 기준으로 판단합니다.

- 같은 이유로 변경되는가
- 같은 검증으로 확인되는가
- 함께 되돌려야 하는가

파일 종류가 다르다는 이유만으로 분리하지 않습니다. 반대로 하나의 파일만 변경하더라도 독립된 책임이 섞여 있다면 분리합니다.

기능, 수정, 리팩터링, 성능, 스타일, 의존성, 빌드, CI 등 목적이 다른 변경은 가능한 한 별도로 다룹니다.

### 3. 커밋은 해당 책임 단위에서 완결되어야 한다

모든 커밋에서 전체 프로그램이 완성되어 있을 필요는 없습니다.

하위 모듈이나 공통 기반도 자체 계약과 검증 방법이 있다면 독립적으로 커밋할 수 있습니다.

다만 히스토리를 만들기 위해 의도적으로 깨진 상태를 남기거나, 나중에 `fix` 커밋을 만들 목적으로 잘못된 구현을 보존하지 않습니다.

### 4. 100줄은 제한이 아니라 재검토 기준이다

수작업으로 작성한 의미 있는 변경이 약 100줄을 넘으면 더 자연스러운 책임 단위로 나눌 수 있는지 다시 검토합니다.

단순히 숫자를 맞추기 위한 다음과 같은 분할은 하지 않습니다.

```text
101 → 100 + 1
102 → 100 + 2
```

100줄을 넘더라도 의미 있는 분리 경계가 없다면 하나의 커밋으로 유지할 수 있습니다.

반대로 100줄 이하라도 서로 독립된 책임이 섞여 있다면 분리합니다.

lockfile, 생성 파일, 단순 이동·이름 변경, 기계적 포매팅 등은 실제 의미 있는 변경량과 구분해서 판단합니다.

### 5. 구현과 검증을 함께 다룬다

테스트는 구현의 부속물이 아니라 해당 변경이 올바름을 증명하는 결과물로 취급합니다.

다음과 같이 하나의 책임을 함께 증명하는 변경은 같은 커밋에 포함할 수 있습니다.

- 기능 + 해당 기능의 최소 계약 테스트
- 버그 수정 + 회귀 테스트
- API 변경 + 해당 API 계약 문서
- 의존성 manifest + 그 결과로 변경된 lockfile

각 커밋에서는 목적에 맞는 최소 검증을 수행하고, 주요 단계와 최종 상태에서는 전체 회귀 및 프로젝트별 릴리스 검증을 수행합니다.

### 6. 변경의 성격에 맞게 검증한다

대표적인 기준은 다음과 같습니다.

```text
code        → build + targeted test
refactor    → build + behavior regression
docs        → link/example/contract consistency
schema      → migration/compatibility validation
build config→ clean build
```

버그 수정은 가능한 경우 실패 재현과 회귀 테스트를 포함합니다.

리팩터링은 외부에서 관찰되는 동작이 유지되는지 검증합니다.

성능 개선은 기준값, 측정 조건과 전후 결과 없이 개선되었다고 주장하지 않습니다.

검증할 수 없는 항목이 있다면 그 이유와 남는 위험을 명확히 기록합니다.

### 7. 문서는 해당 시점의 사실만 기록한다

각 커밋의 문서는 그 시점에 실제로 존재하는 구현과 계약만 설명합니다.

아직 구현되지 않은 기능을 완료된 것처럼 기록하지 않습니다.

API, CLI, schema, 설정, 배포 절차처럼 구현과 직접 연결되는 계약 문서는 관련 변경과 함께 갱신합니다.

최종 `README`, `architecture`, `devlog` 같은 서술형 문서는 구현과 검증이 안정된 뒤 현재 상태를 기준으로 정리할 수 있습니다.

### 8. 커밋 수 자체를 목표로 하지 않는다

커밋을 많게 만드는 것도, 적게 만드는 것도 목표가 아닙니다.

다음과 같은 히스토리 최적화는 하지 않습니다.

- 정확히 100줄 이하로 맞추기 위한 인위적 분할
- 커밋 수를 늘리기 위한 불필요한 세분화
- 커밯 수를 줄이기 위한 독립 책임의 결합
- 히스토리를 그럴듯하게 만들기 위한 가짜 버그, revert 또는 실험 커밋

좋은 히스토리의 기준은 **명확한 책임 경계, 검증 가능성, 정확성, 안전한 롤백**입니다.

## 커밋

기본 형식은 다음을 사용합니다.

```text
type(scope): subject
```

예:

```text
feat(parser): validate quoted arguments
fix(runtime): handle interrupted writes
test(stack): cover empty rotation
refactor(server): separate connection state
docs(readme): document runtime contract
```

커밋 본문은 항상 요구하지 않습니다.

설계 결정, 중요한 버그 수정, 호환성 변경, 보안·성능 변경, 검증 예외처럼 추가 설명이 필요한 경우에만 이유와 검증 결과를 기록합니다.

## 새 프로젝트 추가

새 프로젝트는 기존 프로젝트 브랜치에서 분기하지 않고 독립된 orphan branch로 생성합니다.

작업 전 working tree가 깨끗한지 확인합니다.

```sh
git switch main
git status

git switch --orphan <branch>
```

프로젝트의 초기 파일을 작성한 뒤 첫 커밋을 생성합니다.

```sh
git add <files>
git commit -m "docs(readme): define project scope and development contract"
git push -u origin <branch>
```

예:

```sh
git switch main
git switch --orphan c/new-project

git add README.md
git commit -m "docs(readme): define project scope and development contract"
git push -u origin c/new-project
```

프로젝트 성격에 따라 `c/`, `cpp/`, `web/` 등의 namespace를 사용합니다.

첫 커밋은 프로젝트의 목적, 범위, 기술적 제약과 개발 계약을 정의하는 `docs(readme)` 또는 최소 초기 구조를 만드는 `chore(init)` 성격으로 시작합니다.

각 프로젝트 브랜치는 독립된 Git history를 유지하며 `main` 또는 다른 프로젝트 브랜치에 merge하지 않습니다.

## 프로젝트 확인

원격 프로젝트 브랜치는 다음과 같이 확인할 수 있습니다.

```sh
git branch -r
```

대상 프로젝트로 이동합니다.

```sh
git switch <branch>
```

각 프로젝트의 실행 방법, 구조, 설계와 검증 범위는 해당 브랜치의 `README.md`를 기준으로 합니다.
