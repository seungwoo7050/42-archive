# Project Importance Profile

Project: 42 Archive Portfolio (`web/portfolio`)
Domain: Content-driven portfolio publishing, engineering-evidence presentation, and multi-design web delivery
Primary Purpose: Build a validated, accessible, indexable, and deployable Next.js portfolio that projects one structured evidence model through five complete visual systems and multiple public routes.
Resolved Commit Scope: The complete independent, linear root-to-head history of `web/portfolio`, from `cce7dd020563` through `aff0acdd4cf9`, comprising 476 raw commits. The classification preserves raw positions and includes the three commits excluded from commit-body generation: the root project brief, the generated final laboratory measurement, and the documentation consolidation commit.

## Core Technical Areas

- Structured portfolio, presentation, journey, interview-evidence, résumé, curation, link, technology, and project content modeling.
- Runtime schema parsing, source-aware diagnostics, uniqueness checks, cross-file reference validation, route validation, and repository asset validation.
- App Router state resolution, route availability, canonical template/debug navigation, metadata, not-found behavior, and static project generation.
- A lazy design registry with five full-site renderers, shared route contracts, exhaustive dispatch, and renderer-specific shells.
- Discriminated route view models that resolve cross-content references and limit each renderer to prepared, route-owned data.
- Accessibility across native disclosure controls, focus transfer, landmarks, reduced motion, semantic structures, touch targets, and WCAG regression scans.
- Publication-mode readiness, indexing policy, canonical metadata, sitemap generation, and safely serialized JSON-LD.
- Reproducible build and delivery through pinned runtimes, local assets, standalone output, CI, Docker, and non-root runtime verification.
- Production performance control through prefetch and font boundaries, route-asset measurement, committed growth budgets, Lighthouse gates, and visual/browser matrices.

## Core Architecture

- Authoritative JSON sources enter through strict Zod schemas and source-aware parsing; malformed records never become application data.
- Whole-repository validation sits above file schemas to enforce identifier uniqueness, enabled-route validity, cross-file references, and local asset containment.
- A validated portfolio facade and selectors expose stable domain relationships, placement-aware links, metrics, and availability policy.
- App Router pages own framework concerns: page enablement, query parsing, `notFound`, metadata, JSON-LD, and creation of the route-specific view model.
- Route view models resolve joins once, compute presentation-ready collections, and expose only the data a route is allowed to consume.
- The design registry selects a lazy full-route renderer. Each renderer owns composition and shell presentation but cannot reload or reinterpret the global content graph.
- Build readiness separates permissive template development from strict production publication, then CI verifies the same production artifact that standalone and Docker delivery use.

## Critical Invariants

- Every content source is parsed before selectors or renderers can consume it, and validation reports retain the responsible file and JSON path.
- Identifiers, ordering keys, design registrations, internal routes, project relationships, and referenced assets are unique, resolvable, enabled, and repository-contained.
- Disabled pages and projects are inaccessible at route boundaries and omitted from metadata, sitemap, and production publication surfaces.
- A design advertised by content is supported by code, loadable through the registry, and capable of rendering the complete route set.
- Renderers receive prepared route models rather than the complete content graph; cross-reference resolution has one owner and one missing-reference policy.
- Internal navigation preserves the selected design and debug state, while returning to the configured default removes stale template state.
- Template mode is non-indexable; production mode requires a public origin, publication assets, enabled project exits, and a usable contact method.
- JSON-LD cannot terminate or alter its script context, and machine-readable claims are emitted only from validated production content.
- Skip links move focus, reduced-motion preferences remove nonessential motion, landmarks remain unique, and native disclosure controls preserve focus and hydration state.
- The deployable standalone/container artifact includes static and public assets, runs without root privileges, and is verified through real HTTP requests.
- Performance budgets measure emitted production assets and audited routes; normal checks cannot silently rewrite their baselines.

## Major Engineering Difficulties

- Keeping five visually independent full-site renderers behaviorally consistent across every route without duplicating framework, selection, and relationship logic.
- Migrating from unchecked JSON and broad portfolio objects to strict schemas, aggregate validation, and scoped route projections without breaking the already implemented routes.
- Producing actionable validation for malformed values, duplicate identities, disabled references, unsupported internal routes, and missing or escaping assets in one accumulated report.
- Distinguishing editable template content from publishable content so local previews remain convenient while production builds fail closed.
- Preserving native `<details>` behavior across server rendering, pre-hydration user interaction, explicit closure, and keyboard-focus restoration.
- Verifying the actual Next.js production output: compiler-specific manifests, standalone packaging, local fonts, Tailwind transformation, route bundle cost, Lighthouse thresholds, and Docker asset serving.
