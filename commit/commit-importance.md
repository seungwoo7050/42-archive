# Project Importance Profile

Project: Pong Pong (`ft_transcendence`)
Domain: Full-stack, server-authoritative realtime multiplayer Pong platform
Primary Purpose: Provide browser-based registered and transient-guest Pong, matchmaking, tournaments, social and administrative services, durable PostgreSQL state, and production-grade operation around one authoritative realtime game service.
Resolved Commit Scope: The complete independent, linear history of `web/ft_transcendence`: 433 commits from root `72ac4c1870f` through head `71c5c13480f0`, ordered oldest to newest. No inherited unrelated history or semantic merge commits were present.

## Core Technical Areas
- Strict, versioned HTTP and WebSocket runtime contracts shared by browser, API, and persistence-facing code.
- Cookie authentication, one-time hashed WebSocket tickets, explicit authorization, account suspension, live connection revocation, and transient guest trust chains.
- Deterministic Pong simulation, rating-sensitive AI, fixed-step timing, room state transitions, matchmaking, reconnection, and terminal match handling.
- PostgreSQL migrations, typed row mapping, concurrency control, idempotent match finalization, rating history, friendship invariants, and tournament progression.
- Browser transport lifecycle, reducer-driven game state, input serialization, snapshot ordering/interpolation, and React Query cache ownership.
- Runtime limits, heartbeat, backpressure, graceful drain, readiness, observability, fault injection, production artifacts, containers, and CI verification.

## Core Architecture
- `packages/shared` owns executable transport and domain contracts; API and web consumers parse at their trust boundaries instead of relying on compile-time assertions.
- `PongSimulation` owns mechanics and deterministic state transitions; `GameHub` owns scheduling, authenticated connections, matchmaking integration, snapshots, persistence coordination, and cleanup.
- `RoomSession` owns legal room lifecycle transitions; transport callbacks and rendered snapshots reflect that state rather than defining it independently.
- `Matchmaker` owns queued and reserved player identity, while GameHub retains socket-specific timers and client references.
- `AppRepository` isolates persistence, with PostgreSQL and memory implementations required to preserve the same domain behavior; `finalizeMatch` is the single idempotent result boundary.
- The browser separates socket transport (`GameSocketClient`), state transitions (reducer), React coordination (hook), and presentation (pages/components).
- Production startup, migrations, readiness, draining, metrics, and container orchestration are explicit lifecycle boundaries rather than incidental application code.

## Critical Invariants
- The server is the sole authority for game rules, scores, phases, room membership, matchmaking, and persisted outcomes.
- Every accepted wire message conforms to the supported versioned runtime schema; snapshot and input ordering cannot move state backward.
- One user has one authoritative realtime connection, and reconnect replacement transfers ownership without creating a second match or losing the reserved room side.
- Queue and reservation membership have one owner and are released on every leave, disconnect, rollback, drain, abandonment, failure, and finalization path.
- A logical match result, participant statistics, rating history, and tournament progression commit atomically and idempotently.
- The durable browser session is carried only by an HttpOnly cookie; raw WebSocket tickets are short-lived, single-use, hashed at rest, bounded during authentication, and excluded from logs.
- Suspended users cannot continue privileged HTTP work or retain an already-open realtime control channel.
- Guest identities, matchmaking pools, capabilities, persistence, tickets, leases, and retained results remain isolated and resource-bounded.
- Timers, schedulers, heartbeat handles, retry work, snapshot buffers, and database resources have explicit single-owner cleanup.
- Draining rejects new work immediately, allows owned rooms to finish within a bounded budget, and remains aligned with the container termination grace period.

## Major Engineering Difficulties
- Separating deterministic simulation from connection orchestration without changing the observable realtime protocol.
- Coordinating readiness, pause, disconnect, reconnect, replacement, forfeit, retry, and final cleanup across interacting state machines.
- Preventing duplicate results, ratings, finals, friendship rows, tournament seeds, and admissions under retries or concurrent database operations.
- Authenticating WebSockets without exposing durable session credentials while preserving early messages and bounding unauthenticated buffering.
- Handling slow or stale transports through sequence gates, token buckets, latest-value snapshot delivery, measurable congestion, and hard termination limits.
- Preserving domain correctness during database failure, tournament-start rollback, match-finalization retry, process drain, and deployment shutdown.
- Offering a public guest mode without allowing transient identities to cross into registered data, social features, ratings, or unbounded in-memory resources.
