# 첫 커밋을 실행 가능한 단위로 만들기

## 근거 커밋

| 커밋 | 확인한 변화 |
| --- | --- |
| `a93f4ee` | 패키지 정의와 잠금 파일, Next.js 설정, 콘텐츠 JSON, 루트 레이아웃, `/` 페이지와 Design·Classic의 최소 화면을 함께 추가했다. |

## 문제

설정 파일, JSON, 화면 코드를 따로 커밋하면 각 시점의 저장소가 무엇을 할 수 있는지
모호해진다. 설치는 되지만 경로가 없거나, 데이터는 있지만 소비자가 없는 중간
상태가 생긴다. 이 이력은 첫 커밋의 완료 단위를 “설정이 존재한다”가 아니라
“콘텐츠를 읽어 의미 있는 HTML을 만든다”로 잡았다.

## 이력에서 확인한 첫 실행 경로

`a93f4ee`에는 31개 파일이 들어왔다. 핵심 흐름은 다음과 같다.

```text
package.json + package-lock.json
        ↓
src/content/*.json
        ↓
src/lib/portfolio.ts
        ↓
src/app/layout.tsx + src/app/page.tsx
        ↓
Design 또는 Classic 홈
        ↓
서버가 만든 HTML
```

첫 커밋의 경계는 다음과 같이 나뉜다.

| 영역 | 포함한 것 | 뒤로 미룬 것 |
| --- | --- | --- |
| 설치 | 패키지 정의, 잠금 파일, TypeScript·ESLint·PostCSS·Next 설정 | 테스트·성능·컨테이너 전용 도구 |
| 콘텐츠 | 홈이 실제로 읽는 프로필·표현 설정 등 11개 JSON과 정적 타입 | Zod 스키마, 파일 간 참조와 자산 검사 |
| 요청 | 루트 레이아웃, favicon, 전역 CSS, `/` 페이지 | 목록·상세·지원 경로와 404 처리 |
| 표현 | Design과 Classic의 최소 홈, 공통 표시 컴포넌트 | 세 개의 추가 디자인과 전체 경로 행렬 |
| 명령 | `dev`, `build`, `start`, `lint`, `typecheck` | 아직 구현되지 않은 검사 명령 |

명령 이름만 미리 만들어 성공하는 빈 스크립트는 두지 않았다. Vitest와
Playwright 명령은 실제 설정과 첫 검사가 생긴 뒤에 추가됐다.

## 무엇을 보장했고, 무엇을 보장하지 않았나

첫 커밋의 `build` 명령은 루트 페이지와 서버 렌더링 진입점이 서로 연결돼 있는지
확인할 수 있는 수단이었다. 그러나 커밋에 명령이 포함됐다는 사실만으로 당시 실행
결과까지 증명되지는 않는다. 브라우저 상호작용, 공개 콘텐츠의 적절성, 컨테이너
실행도 이 단계의 범위가 아니었다.

정적 타입 역시 JSON 값 자체를 검사하지 않았다. 당시 코드는 import한 값을 수기
타입으로 단언했다. 따라서 키 오타나 잘못된 참조 ID는 컴파일 뒤까지 남을 수
있었다. 이 한계가 [01. 타입과 선택 정책](./01-content-contract-and-selectors.md)과
[06. 실행 시 콘텐츠 검증](./06-runtime-content-boundaries.md)으로 이어졌다.

## 현재 코드와 구분하기

현재 `/` 페이지는 콘텐츠를 직접 조립하지 않는다.
`resolvePortfolioPageContext()`가 URL 상태를 해석하고,
`createHomeViewModel()`이 화면 입력을 만든 뒤 레지스트리가 렌더러를 고른다.
빌드 앞에는 콘텐츠 검사도 연결돼 있다. 이는 첫 커밋 뒤에 추가된 구조이므로 당시의
완료 조건으로 소급하지 않는다.

## 남긴 원칙

첫 기능 단위는 다음 질문에 모두 답할 수 있어야 한다.

1. 어떤 명령으로 설치하고 실행하는가?
2. 어떤 입력을 실제로 소비하는가?
3. 어느 URL에서 결과를 관찰하는가?
4. 실패하면 어느 단계에서 멈추는가?
5. 아직 검증하지 않는 범위는 무엇인가?

이 다섯 항목을 한 커밋에서 연결하면 이후 리팩터링도 “파일이 늘었다”가 아니라
실행 경계가 어떻게 이동했는지 비교할 수 있다.
