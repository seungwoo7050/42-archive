# 포트폴리오 재구현 기록

이 문서 묶음은 하나의 콘텐츠를 다섯 가지 디자인으로 보여 주는 포트폴리오를
어떻게 확장했는지 설명한다. 완성된 기능을 나열하기보다, 구현 과정에서 책임의
경계가 왜 바뀌었고 어떤 실패가 다음 변경을 이끌었는지 추적한다.

감사 기준은 `web/portfolio-rewrite`의 `8db290d`다. 기존 문서가 인용한 구현
커밋 87개의 해시와 당시 기록된 제목을 이 기준의 Git 이력과 대조했다. 통합한
본문도 87개 해시를 모두 남겼지만, 반복 목록 대신 장별 전환점으로 묶었다. 다만
명령이나 기준값이 저장소에 있다는 사실만으로 현재 실행 결과까지 통과했다고
주장하지 않는다.

## 기록을 읽는 법

각 장은 다음 세 종류의 근거를 구분한다.

- **이력**: 해당 커밋의 실제 변경 내용이다. 당시 코드와 지금 코드를 섞지 않는다.
- **현재**: 감사 기준 커밋에서 확인한 구조와 동작이다.
- **남은 위험**: 현재 코드나 검사 범위에서 확인되는 빈틈이다. 실제로 발생하지 않은
  장애를 과거 사건처럼 꾸미지 않는다.

코드 조각은 이해에 필요한 부분만 싣는다. 과거 코드는 커밋을 명시하고, 현재 코드는
파일 경로를 적는다. 설명을 위해 만든 반례는 저장소에서 실제로 시도한 구현과
구별한다.

## 감사 기준의 현재 구조

감사 기준 커밋에서 확인한 사실은 다음과 같다.

- `src/content/`의 JSON 14개를 서버 모듈이 읽고 Zod 스키마와 파일 간 참조
  검사에 통과시킨다.
- 공개 경로는 홈, 프로젝트 목록·상세, About, Resume, Contact, Journey,
  Interview Map의 여덟 종류다.
- Design, Classic, Editorial, Brutalist, Cinematic 다섯 디자인이 같은 라우트
  뷰 모델을 서로 다른 문서 구조로 표현한다.
- 저장소가 직접 선언한 클라이언트 컴포넌트는 `AnimatedTerminal`과
  `DesignSwitcherClose` 두 개다. 프레임워크의 클라이언트 런타임까지 없다는 뜻은
  아니다.
- 빌드는 webpack과 standalone 출력을 사용하며, 컨테이너 검사는 비루트 실행과
  JSON이 가리키는 정적 자산의 HTTP 응답을 확인한다.

이 목록은 구조를 찾기 위한 지도이지 품질 보증서가 아니다. 예를 들어 브라우저
검사는 Chromium 프로필을 사용하고, Lighthouse 기준값은 통제된 로컬 측정이며,
콘텐츠 준비 검사는 경력이나 성과 문구의 사실성을 판정하지 않는다.

## 검증 표현의 기준

본문에서 “검증한다”는 말은 해당 검사가 직접 관찰하는 범위로 제한한다.

- 타입 검사는 실행 시 JSON 값이나 화면 배치를 확인하지 않는다.
- jsdom 검사는 실제 CSS, 네트워크, 브라우저의 포커스 처리와 같지 않다.
- Playwright와 axe 통과가 모든 브라우저·보조 기술·수동 접근성 검토를 대신하지
  않는다.
- 파일 존재 검사는 이미지 디코딩이나 최종 컨테이너의 HTTP 제공을 뜻하지 않는다.
- 저장된 성능 기준값은 새로 측정한 현재 결과가 아니다.

이 구분을 유지해야 구현 기록이 성공담이 아니라 다음 변경을 판단할 수 있는
근거가 된다.
